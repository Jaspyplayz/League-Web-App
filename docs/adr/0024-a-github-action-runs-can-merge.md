# 0024: A GitHub Action runs can-merge when a PR's checks finish

Status: draft (JAS-121). Jasper accepts it by merging the PR. It takes up the option [0008](0008-agents-merge-two-way-doors.md) left out ("A GitHub Action that merges"); 0008 stays as it was written.

## Context

`npm run can-merge -- <pr> --merge` ([0008](0008-agents-merge-two-way-doors.md), [0013](0013-can-merge-uses-github-rest.md)) is the only way Claude Code merges its own PRs, and something has to run it once every check has finished. On 2026-10-31 nothing did: PRs 234, 235 and 238 each waited for Jasper or a local session. The cloud's permission check refused `can-merge --merge` as "an unrequested commit in a connected app" (PR 234), and a builder that has finished can't wait around for the last check anyway. A watcher script on Jasper's PC would only work while it's on. Jasper chose a GitHub Action.

## Options considered

1. **A watcher on Jasper's PC** that polls open Claude PRs. Nothing new in `.github/`, but nothing merges while his PC is off.
2. **GitHub's auto-merge.** It sees only the required checks, not the tier, the builder, the risky list or the ticked criteria. 0008 ruled it out for that.
3. **A workflow that runs `can-merge --merge` from main when a check finishes (chosen).** The gates stay in one place and run unchanged.

For holding a PR until its builder is done, a draft PR was the first idea, since can-merge already refuses drafts. But GitHub's REST API can't mark a PR ready for review (only GraphQL can, and a cloud session can't reach GraphQL), so a cloud builder could never let its own draft go. A line in the description works over REST.

## Decision

Option 3: `.github/workflows/agent-merge.yml`, with `scripts/can-merge-action.ts` and its pure, tested decisions in `scripts/can-merge-action-steps.ts`.

- **When:** `workflow_run`, `completed`, on CI, Reviewer, Smoke test and Dependency review: every named workflow that puts a check on a PR. The job runs only for a successful run on a branch that starts `claude/` in this repo; anything else shows as a skipped run with no runner. The script checks the branch and repo again so it's safe on its own.
- **Which PR:** the open PR whose head is that branch in this repo (`GET pulls?state=open&head=<owner>:<branch>`), checked again against the answer's own head branch and repo. The run's own `pull_requests` list is often empty for Smoke test, which starts from a deployment, so the branch is the one key every run has.
- **When it's ready:** only a PR whose description says `**Ready to merge:** yes at <head sha>`, read with the same field reader as the **Tier:** and **Builder:** lines, so a hidden or doubled line holds it. Naming the commit means a push after it, such as a fix the builder found it needed and then a postmortem entry for it, holds the PR again until the builder names the new head; a bare yes, or a yes with a condition after it, holds it too. Every gate can pass before the builder has finished: a tiny PR skips the reviewer and has no criteria, so its checks can pass before its screenshots, and a normal PR's verdict lands before its postmortem entry. The PR template opens with `no`, and the builder edits it to yes at the head as its last step, which reruns Reviewer, which runs this. Setting it back to no holds a PR. It's the Action's rule, not a can-merge gate, so the gates didn't change and a session running can-merge itself isn't held by it.
- **What runs:** `npm ci`, then `can-merge --merge` on the PR, from main. A `workflow_run` workflow always runs as it is on main, and the job checks out main with `persist-credentials: false`. The PR's code is never checked out or run; can-merge only reads it through `git fetch` and the REST API. A test pins every step, every checkout and setup option, and every line that reads the event or the token, so a change to any of them must change the test too. `actions/checkout` uses the job's token for its one fetch of main; only the last step gets it in its environment, and `npm ci` never does. The job turns setup-node's npm cache off.
- **Refusal versus crash:** can-merge now exits with 2 when a gate fails (`REFUSED_EXIT_CODE` in `scripts/can-merge-gates.ts`) and 1 on any error, Node's code for an uncaught one. A refusal is the usual result, since most checks finish while another is still running, so it passes with a notice and a line in the run's summary. A crash before the merge is often a race (the builder pushed mid-check, or another branch merged first and GitHub answered "Base branch was modified"), so the script tries once more after 30 seconds. A second crash, a merge whose comment or label then fails, or a merge whose CI on main GitHub won't start (JAS-123), turns the run red, and the summary says whether the PR merged.
- **Races:** a concurrency group per branch keeps one run going at a time. A running one is never cancelled, since it may be mid-merge, and a queued one is replaced by the newest, which reads the latest state anyway. The merge request names the head commit the gates checked, so GitHub refuses it if the PR moved.
- **Token:** the job's built-in `GITHUB_TOKEN`, with `contents`, `pull-requests` and `issues` write, and `checks` and `statuses` read for what can-merge reads. `actions` is write, not read, so the job can start CI on main after a merge (the first open question, JAS-123).

## The three open questions

1. **Token.** GitHub doesn't start workflows for events the built-in token causes, apart from `workflow_dispatch`, `repository_dispatch` and some `pull_request` events ([GitHub docs: GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token)). So the merge commit this workflow pushes to main gets no `CI` push run. The PR's own CI passed at its head commit, but the ruleset doesn't ask for a branch to be up to date before merging, so two PRs that each pass alone can break main together, and with most merges made by this workflow, main's own CI may rarely run at all. Only a merge by a person (Jasper's or Dependabot's PRs) starts it, and Vercel's production build is the only other check, since Vercel deploys main through its own app. Two fixes: a GitHub App token keeps the push run and shows the app as the merger, but Jasper would create the app, install it, add two secrets, and the workflow would need `actions/create-github-app-token`, a new dependency. Or, after a merge, this workflow starts CI on main with `workflow_dispatch`, which the token can start.

   **Answered (JAS-123):** Jasper chose `workflow_dispatch` on 2026-10-31, since `ci.yml` is the only workflow that runs on pushes to main and it needs no app, secret or new dependency. GitHub's docs say "`workflow_dispatch` and `repository_dispatch` events always create workflow runs" ([Triggering a workflow from a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)). Whenever a PR merged, whether can-merge passed or crashed after the merge, `mergePull` in `scripts/can-merge-action-steps.ts` calls `POST repos/{owner}/{repo}/actions/workflows/ci.yml/dispatches` with `{"ref": "main"}`. The job's `actions` permission went from read to write for that, and `ci.yml` gained a `workflow_dispatch:` trigger; its token still only reads. If GitHub refuses, the run turns red and its summary says the PR merged anyway and how to start CI by hand (Actions tab, CI, Run workflow). The run shows as event `workflow_dispatch`, not `push`, and starts on main's latest commit at that moment, which is the merge commit unless another merge landed in between, in which case it checks both. When that CI run finishes, it starts this workflow again, but on `main`, so the job's `if:` skips it with no runner.
2. **Ruleset.** Main's "Protect Main Branch" ruleset has `require_extra_approval_for_unattributed_changes` on. GitHub's docs describe it as one more approval for a PR Copilot opens that isn't attributed to a person, and say it has no effect when the ruleset requires zero approvals ([GitHub docs: available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)). The ruleset requires 0 approvals (`gh api repos/Jaspyplayz/League-Web-App/rulesets/25086024`), and Claude's PRs are opened by Jasper's account, not Copilot. So it shouldn't block `github-actions[bot]`. The ruleset has no bypass actors, so the bot's merge passes the same `check`, `Vercel` and `reviewer` checks a person's does. Unchanged.
3. **Vercel check.** Vercel's status comes from its app and starts no workflow run. The smoke test starts from Vercel's "deployment succeeded" event and takes one to two minutes, so Vercel's status is in before it finishes. On the 40 most recent Claude PRs (up to #239), Vercel's status was set before the smoke test finished on every one. CodeQL's checks start no workflow this can name either: theirs is a "dynamic" workflow named after the PR ("PR #240"). On the same 40 PRs, CodeQL never finished after the last of the four workflows.

## Consequences

- A cloud builder's tiny or normal PR merges once it's marked ready and its last check passes, with no Claude session open. The merge comment and the `merged-by-claude` label are added as before, and the merge commit carries the same marker the revert gate reads.
- GitHub shows `github-actions[bot]` as the merger instead of Jasper.
- The agent no longer needs merge rights to finish a PR, which closes part of the gap 0008 named: the Action runs main's gate code, not a copy in the builder's folder. Jasper's credentials in a session can still merge, so the ruleset stays the lock.
- No person reads can-merge's output before a merge any more. The gates read the PR's own words (tier, builder, verdict, ticks, ready line), so anyone who can push a `claude/` branch here and write that text could get a PR merged. That should be only Jasper's account, which Claude's sessions use; the cloud couldn't read the collaborator list to confirm it. This was already true of a session running can-merge; it's accepted, not new.
- A refusal shows only on the run's page and main's commit, not on the PR. So after marking a PR ready, the builder runs can-merge without `--merge` and fixes any gate other than checks still running (docs/workflow.md step 11). A gate that fails after the builder has left, such as Jasper turning agent merging off, holds the PR silently.
- A PR waits for the next run, or a session running can-merge, when none of the four workflows finishes after its gates could pass: a change no workflow reruns for (a label), CodeQL finishing last (it can't be named in the trigger list), a gate code or `package.json` change merged to main in the minute between this job's checkout and can-merge's own fetch (the "Gate code matches main" gate refuses), or two crashes in a row. A scheduled sweep of open `claude/` PRs, or a `workflow_dispatch` trigger with a PR number, would cover these; neither is built yet.
- A parent ticket's move to Done after its last sub-ticket merges falls to the builder if its session sees the merge, or Jasper's weekly read, since this workflow can't reach Linear.
- More Actions runs: up to four short ones per push to a Claude branch, each `npm ci` plus can-merge, and a skipped one on main's latest commit for every other run. Each merge also starts one CI run on main, as a push by a person always did. The repo is public, so they're free. A crash shows as a red run on main's latest commit, which can read as "main is broken"; the run's summary says which PR it was.
- `actions/checkout` and `actions/setup-node` are pinned by major tag, like the other workflows. This is the only job with write access, so pinning these two to commit SHAs is the usual hardening, and Jasper's call.
- The wellness routine's prompt in `docs/wellness.md` changed to write the ready line and stop running `--merge`; the routine itself needs the merged prompt pasted in.
- It runs for the first time once this PR merges, since `workflow_run` runs only from the default branch.
- Reverting this PR stops the Action, and `npm run can-merge` works from a session as before. Merges and comments it made stay.
